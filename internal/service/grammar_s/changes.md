# 变更记录

## 修复ε处理不当问题

### 问题描述
前后端将空字符串""当作ε处理，导致文法化简过程中对ε产生式的处理错误。

### 修复内容

#### 1. 修改 `RemoveEpsilonProductions` 函数
- **文件**: `simplify.go:143`
- **变更**: 将空产生式的判断条件从 `len(p.Right) == 0` 改为 `len(p.Right) == 1 && p.Right[0] == model.Epsilon`
- **作用**: 正确识别ε产生式，确保在去除空产生式时只跳过真正的ε产生式

- **文件**: `simplify.go:194`
- **变更**: 保留S→ε产生式时使用 `[]model.Symbol{model.Epsilon}` 而非空切片
- **作用**: 确保S→ε产生式的表示正确，使用model.Epsilon符号而非空字符串

#### 2. 修改 `getNullableVariables` 函数
- **文件**: `simplify.go:208`
- **变更**: 将空产生式的判断条件从 `len(p.Right) == 0` 改为 `len(p.Right) == 1 && p.Right[0] == model.Epsilon`
- **作用**: 正确识别ε产生式，确保可空变量集的计算正确

- **文件**: `simplify.go:219`
- **变更**: 同样修改跳过空产生式的判断条件
- **作用**: 确保在迭代过程中正确跳过ε产生式

#### 3. 修改辅助函数
- **文件**: `simplify.go:316` (isAllTerminal函数)
- **变更**: 添加 `s != model.Epsilon` 检查
- **作用**: 确保在判断是否全为终结符时，正确处理ε符号

- **文件**: `simplify.go:329` (canDeriveUsingSet函数)
- **变更**: 添加 `s != model.Epsilon` 检查
- **作用**: 确保在判断是否可使用给定集合推导时，正确处理ε符号

- **文件**: `simplify.go:345` (allInSet函数)
- **变更**: 添加 `s == model.Epsilon` 检查
- **作用**: 确保在判断符号是否在集合中时，正确处理ε符号

### 修复效果
- 统一使用 `model.Epsilon` 符号表示空产生式，不再将空字符串""当作ε处理
- 确保文法化简过程中对ε产生式的处理正确
- 提高了代码的一致性和可靠性，避免了因ε处理不当导致的错误

### 影响范围
- 仅影响文法化简相关功能，不影响其他模块
- 对前端和后端的ε处理逻辑进行了统一，确保数据一致性

## 优化生成字符串算法性能

### 问题描述
生成字符串算法在处理复杂文法时可能会遇到性能问题，主要表现为：
1. 生成过多字符串导致内存占用过高
2. 队列无限增长导致内存溢出
3. 验证过程耗时过长

### 优化内容

#### 1. 优化 `util.GenerateStrings` 函数
- **文件**: `pkg/util/util.go:42`
- **变更**: 添加 `maxStrings` 变量，限制最大字符串数量为1000
- **作用**: 避免生成过多字符串导致内存占用过高，防止指数爆炸

- **文件**: `pkg/util/util.go:65`
- **变更**: 移除调试打印语句 `fmt.Println("len:", len(result), " maxlen:", maxLen)`
- **作用**: 减少不必要的输出，提高性能

#### 2. 优化 `generateAcceptExampleString` 函数
- **文件**: `generate.go:90`
- **变更**: 添加 `seenForms` 映射，避免重复处理相同的句型
- **作用**: 减少重复计算，提高算法效率

- **文件**: `generate.go:108`
- **变更**: 添加 `maxQueueSize` 变量，限制队列大小为1000
- **作用**: 避免队列无限增长导致内存溢出

- **文件**: `generate.go:109`
- **变更**: 在循环条件中添加 `len(queue) < maxQueueSize` 检查
- **作用**: 确保队列大小不超过限制，防止内存溢出

- **文件**: `generate.go:116-119`
- **变更**: 添加对 `seenForms` 的检查，跳过已处理过的句型
- **作用**: 减少重复计算，提高算法效率

- **文件**: `generate.go:154-160`
- **变更**: 在添加新句型到队列前，检查是否已处理过
- **作用**: 避免重复处理相同的句型，减少队列大小

#### 3. 优化 `generateRejectExampleString` 函数
- **文件**: `generate.go:190-193`
- **变更**: 限制最大字符串长度为5
- **作用**: 避免生成过长字符串，减少验证时间

- **文件**: `generate.go:198-199`

- **作用**: 确保验证次数不超过限制，防止性能问题

- **文件**: `generate.go:208`

- **作用**: 确保验证次数不超过限制

### 优化效果
- 显著提高了生成字符串算法的性能，尤其是在处理复杂文法时
- 避免了内存溢出和性能瓶颈问题
- 保持了生成结果的质量，仍然能够生成有效的接受和拒绝字符串示例

### 影响范围
- 仅影响字符串生成相关功能，不影响其他模块
- 对用户体验有明显改善，减少了等待时间

## 优化二义性检查算法

### 问题描述
二义性检查算法存在以下问题：
1. 错误地将 [a] 和 [a, ε] 视为同一状态，导致无法正确检测二义性
2. 缺少状态重复检测，导致算法效率低下
3. 深度计算不准确，可能导致无限循环
4. 包含调试打印语句，影响性能

### 优化内容

#### 1. 优化 `symbolsToStringJoinSep` 函数
- **文件**: `ambiguity_check.go:10-21`
- **变更**: 重新实现符号转换逻辑，使用 "|" 作为分隔符，确保 [a] 和 [a, ε] 被正确区分
- **作用**: 解决状态识别错误的问题，确保不同状态被正确区分

#### 2. 优化 `IsAmbiguousRegular` 函数
- **文件**: `ambiguity_check.go:43`
- **变更**: 添加 `visited` 映射，记录已处理的状态
- **作用**: 避免重复处理相同状态，提高算法效率

- **文件**: `ambiguity_check.go:45-48`
- **变更**: 在 `state` 结构体中添加 `depth` 字段，记录实际推导深度
- **作用**: 更准确地控制搜索深度，防止无限循环

- **文件**: `ambiguity_check.go:57`
- **变更**: 使用 `curr.depth` 进行深度检查，替代 `flattenSymbols` 函数
- **作用**: 更准确地控制搜索深度，避免因符号长度计算不准确导致的问题

- **文件**: `ambiguity_check.go:63-69`
- **变更**: 重新实现句子生成逻辑，正确处理ε符号
- **作用**: 确保句子生成正确，避免因ε处理不当导致的错误

- **文件**: `ambiguity_check.go:77-82`
- **变更**: 添加状态重复检测，跳过已处理的状态
- **作用**: 提高算法效率，避免重复计算

- **文件**: `ambiguity_check.go:88-91`
- **变更**: 在添加新状态时，正确设置 `depth` 字段
- **作用**: 确保深度计算准确，防止无限循环

- **文件**: `ambiguity_check.go:54, 73`
- **变更**: 移除调试打印语句
- **作用**: 提高性能，减少不必要的输出

### 优化效果
- 解决了 [a] 和 [a, ε] 被错误视为同一状态的问题
- 提高了二义性检查算法的效率，避免重复处理相同状态
- 更准确地控制搜索深度，防止无限循环
- 提高了算法的稳定性和可靠性

### 影响范围
- 仅影响二义性检查相关功能，不影响其他模块
- 对用户体验有明显改善，减少了二义性检查的时间
